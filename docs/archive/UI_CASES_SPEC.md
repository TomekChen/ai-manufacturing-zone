# 界面美化 + 案例库 · mini-SPEC（草案，开工前与老板对齐）

> 背景：老板两条明确诉求——
> 1. **"界面看起来太简单"**：门户/架构图/知识库问答/后台整体观感要提升一档。
> 2. **"包括我们的一些案例"**：要能沉淀并展示团队的智能制造落地案例，
>    而且这些案例应该反过来喂给已上线的 PRD 生成器，让它产出的《AI 智能体平台转型 PRD》
>    带"我们真实做过"的行业参考与案例（呼应老板"做行业 know-how 专家"的定位）。
>
> 本草案把这两件事作为**两个可独立交付的垂直切片**来规划：
> - **Slice A：界面整体美化**（纯前端 + 设计 token，零后端）
> - **Slice B：案例库**（后端 + 管理端 CRUD + 公开展示 + 打通 PRD 生成器）
>
> 先做哪个由老板定，默认建议 **B（案例库）先行、A 随后**——因为案例库直接增强 PRD 生成器
> 这个老板最兴奋的功能、产出可被感知的业务价值；美化是锦上添花。二者不冲突。
>
> 状态：**草案，未开工**。目的是先对齐范围、接口、验收标准，避免闷头做偏。

---

## 一、Slice A：界面整体美化

### A1. 目标
- 沿用现有 React + Vite 单页结构，**不重写信息架构、不改后端接口**，只提升视觉与交互质感。
- 对齐 `beautiful-pages` 规范（Apple / Stripe / Linear / Vercel 那套克制、专业、有呼吸感的设计语言）；
  这是 to B / 政企 + 智能制造调性，**稳重专业优先，不花哨**。
- 把散落在 `style.css` 里的硬编码色值/间距，收敛成一套**设计 token（CSS 变量）**，后续加页面可复用。

### A2. 范围（现状 → 目标）
现状页面清单（公开侧）：顶部导航、Hero、架构图 `ArchitectureDiagram`、
知识库问答 `KnowledgeQA`、`DocPreview`、页脚友情链接 `LinkFooter`；后台 `main.jsx` 六个页签。

本切片覆盖（按优先级，可再分批）：
1. **公开门户首屏 / Hero**：第一眼印象，重做排版层次、留白、渐变/微交互、CTA 按钮。
2. **架构图区块**：统一卡片风格、层级配色、悬停反馈。
3. **知识库问答区**：输入区、答案气泡、来源标注卡片的观感；流式/loading 态更精致。
4. **后台整体**：导航页签、表单、表格、按钮、状态徽标的统一视觉语言（复用 PRD 页已有 `.prd-*` 风格并抽公共类）。
5. **响应式与暗色主题**：移动端断点收敛；沿用现有暗色变量，必要时补一套亮色 token。

### A3. 非目标
- 不改任何后端接口 / 数据结构 / 路由。
- 不引重型 UI 库（Tailwind / MUI / shadcn）——现有是手搓 CSS，保持零新依赖；
  如老板坚持要组件库，另开决策项评估。
- 不做品牌 VI（logo、字号体系若无设计稿，沿用现状微调）。

### A4. 验收标准（怎么算"变好看了"）
- 首屏在 1440px / 390px 两档下无错位、对比度达标（正文 ≥ 4.5:1）。
- 全站按钮/卡片/输入框/表格有统一圆角、阴影、间距节奏（8pt 栅格）。
- 关键交互（hover / focus / loading / 空态 / 错误态）都有明确视觉反馈。
- `npm run build` 通过；改动纯 CSS + JSX className，回归无破坏。
- 老板肉眼确认"不简单了"（主观项，需一轮反馈）。

### A5. Seam（可测边界）
- 纯样式，无逻辑 seam；以"构建通过 + 截图对比"为信号。
- 建议做法：先在**一个页面**（推荐公开首屏）打出设计 token + 组件范式样板，
  老板认可后，其余页面按样板批量套用——**垂直切片、先样板后铺开**，避免一次改到底又不对味。

## 二、Slice B：案例库

### B1. 目标
- 团队能在后台**录入/编辑/上下架**"客户案例"，字段结构化：
  客户（可匿名）、行业、场景/痛点、解决方案、关键智能体/功能、**量化成效**、周期、可公开标记。
- 前台有**案例展示区**（可筛选：行业 / 场景），提升"我们真做过"的说服力。
- **打通 PRD 生成器**：已发布（`status=approved` 且 `public=true`）的案例进知识库索引，
  生成 PRD 时优先作为"行业参考与案例"注入，并在来源里标注"案例"。

### B2. 数据模型
两种落地路径（**需老板/我们二选一**）：

- **方案 B-1（复用 KB store，推荐，最小改动）**：
  案例仍是一条 `doc`，`type="case"`，新增可选 `category` 与结构化 `meta` 字段存进 `kb_docs.json`；
  正文由结构化字段拼成一段 markdown 喂给 `add_text(doc_type="case", status="approved")` → 自动切块、嵌入、入索引。
  好处：天然被 RAG 检索到，PRD/问答都能用；与现有 `docs/stats/search` 完全同构。

- **方案 B-2（独立 cases.json + 派生入库）**：
  单独存 `data/cases.json`（结构化），"发布"动作时把案例正文写入 KB（`type="case"`）；下架时删除对应 doc。
  好处：结构化 CRUD 与检索解耦、字段更自由；代价：多一层同步逻辑。

倾向 **B-1**：案例字段本就不多，直接给 doc 加 `meta`（`industry`/`outcome`/`public`/`tags`）即可，
少一套存储、少一层同步。

### B3. 接口契约（草案）
公开侧：
- `GET /api/cases` → `{cases:[{id,title,industry,tags,outcome,summary,updated_at}], facets:{industries:[...]}}`（仅 public+approved）
- `GET /api/cases/<id>` → 详情（痛点/方案/智能体清单/成效）

后台侧（`@require_admin`，`Authorization: Bearer`）：
- `GET  /api/admin/cases`（含未发布/未公开）
- `POST /api/admin/cases`（新建/草稿）
- `PUT  /api/admin/cases/<id>`（编辑）
- `POST /api/admin/cases/<id>/publish`（上架 → 入 KB 索引）
- `POST /api/admin/cases/<id>/unpublish`（下架 → 从索引摘除）
- `DELETE /api/admin/cases/<id>`

请求体（新建示例）：
```json
{
  "title": "某汽车零部件厂 AI 视觉质检",
  "industry": "汽车零部件",
  "customer": "某 Tier1 供应商（可匿名）",
  "pain_point": "人工抽检漏检率高、缺陷知识不沉淀…",
  "solution": "部署质检智能体 + 缺陷知识库 + MES 对接…",
  "agents": ["质检智能体", "设备预测维护智能体"],
  "outcome": "漏检率↓、MTTR 从 4.2h→1.5h（示例）",
  "duration_weeks": 12,
  "public": true
}
```

### B4. 打通 PRD 生成器（闭环）
- `rag/prd.py::format_kb_context`：命中片段按其 doc `type=="case"` 归类，
  单独成一段"【我们相关案例】"，与"【行业参考资料】"区分，标注来源标题。
- `generate_prd` 的检索：对 case 类型做**轻微加权/保底 N 条**（如 top_k 里至少留 1–2 个 case 名额），
  避免长文档淹没案例。配置项 `PRD_CASE_MIN`（默认 1，env 可覆盖）。
- 输出契约新增 `case_sources`（本次引用了哪些案例），前端 PRD 结果区展示"参考案例"徽标。

### B5. 管理端 & 前台 UI
- 后台：`main.jsx` 加"案例库"页签 → `AdminCases.jsx`（列表 + 新建/编辑表单 + 发布/下架），复用现有后台样式。
- 前台：门户加"客户案例"区块（卡片栅格 + 行业筛选 + 详情弹层，复用 `DocPreview` 式弹层范式）。

### B6. 非目标
- 不做案例富文本编辑器（先结构化字段 + 纯文本/简单 Markdown）。
- 不做案例图片/视频上传（首版文字为主；配图留后续）。
- 不做案例权限分级 / 多人协作编辑（MVP 团队内部用）。
- 不引新依赖（复用 `KnowledgeStore` + 现有 `chat`/`search`）。

### B7. 可测边界（Seam，TDD）
- 纯函数：`build_case_doc_text(fields)`（结构化字段→入库正文）、`clean_case_input(payload)`（校验）、
  `classify_hits(hits)`（把命中分成 案例 / 行业资料）、`select_prd_cases(hits, min_cases)`。
- 单测（离线，假 store）：案例 CRUD 校验、发布/下架对索引的影响、`format_kb_context` 案例分段、
  PRD 保底纳入 case、`case_sources` 正确回传。
- 冒烟：登录→建案例→发布→`/api/cases` 可见→调 `/api/admin/prd/generate` 返回里 `case_sources` 非空。

### B8. 向后兼容 / 上线
- 给 doc 加 `meta`/`type="case"` 用 `.get()` + 默认值，旧 8 篇文档照常加载。
- 上线走既有 `source/` 打包约定（备份 source/data + 回滚镜像 tag），与 PRD 上线同流程。

## 三、建议排期与开工前需老板拍板的点

建议顺序：**B 案例库（先样板 PRD 闭环）→ A 界面美化（先首屏样板，认可后铺开）**。

需老板确认（影响范围，开工前对齐）：
1. 案例**能否公开**：哪些可署真名、哪些必须匿名？公开案例放门户哪个位置？
2. 案例字段够不够：上面 B2/B3 字段是否覆盖老板心里"一个好案例"该有的信息？有没有要加的（如合同额级别、部署形态公有/私有）？
3. 美化的"好看基准"：有没有老板喜欢的参考站点/竞品截图？先做**首屏样板**给他看再决定铺不铺开，可以吗？
4. 两件事的**先后与投入**：先案例库、还是先美化？要不要并行？

## 四、和已上线功能的衔接
- PRD 生成器（§二十一已上线）：B 的 `format_kb_context` / `select_prd_cases` 直接增强其产出质量，无需改已上线接口签名，只在结果里加 `case_sources`（增量字段，向后兼容）。
- 知识库（RAG 6 切片）：案例复用同一套 chunk/embed/search 栈，零新依赖。
